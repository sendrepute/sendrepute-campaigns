# SendRepute Campaigns

Автономні (self-hosted) аудиторії, кампанії, шаблони, автоматизації та розсилки з
вашого власного сервера. Цей репозиторій поширює **скомпільоване середовище виконання**, а не повний
вихідний код монорепозиторію.

![Попередній перегляд десктопної версії SendRepute Campaigns](docs/assets/campaigns-github-desktop.jpg)

Спробуйте [інтерактивне демо](https://www.sendrepute.com/campaigns/?demo=true)
(без реальних повідомлень, хмарних конструкторів чи платних результатів).

<a id="quickstart-fresh-ubuntu-24042604"></a>

## Швидкий старт: чиста Ubuntu 24.04/26.04

На **новому сервері без наявної інсталяції Campaigns** виконайте:

```sh
sudo apt-get update
sudo apt-get install -y git
git clone https://github.com/sendrepute/sendrepute-campaigns.git
cd sendrepute-campaigns
./setup.sh
```

Процес встановлення (Setup) запитує, який режим доступу обрати, і використовує наявні робочі Docker/Compose; на
чистому підтримуваному сервері Ubuntu без Docker він просить дозволу на встановлення
пакетів Ubuntu. Він не видаляє Snap Docker і не обходить AppArmor. Не
клонуйте репозиторій поверх наявної інсталяції; див. [Оновлення](#update).

**CAMPAIGNS READY FOR OWNER SETUP** означає, що програма справно працює у своєму
контейнері, а не те, що налаштування власника завершено або публічний HTTPS перевірено.
Для HTTPS спершу перевірте виведену сторінку інсталяції з іншої мережі:
вона повинна мати дійсний, довірений сертифікат без жодних попереджень у браузері. Якщо
сертифікат перебуває в стані очікування або є недійсним, у **жодному разі** не вводьте жодних секретних даних.

Для нового власника одноразовий токен є **обов'язковим**, а не опціональним. Щойно
обраний режим доступу буде готовий, виконайте це на VPS **із каталогу проєкту**:

```sh
sudo docker compose exec campaigns cat /var/lib/sendrepute-campaigns/installer-token
```

Пропустіть `sudo`, якщо ваш обліковий запис Docker цього не вимагає. Скопіюйте вивід команди
та вставте його в поле **Setup token** на виведеній сторінці інсталяції.
Заповніть дані власника та відповідну публічну URL-адресу (Public URL), що закінчується на `/campaigns/`,
потім завершіть активацію SendRepute та налаштування власника в майстрі. Процес встановлення
**не** виводить токен автоматично. Ніколи не вставляйте його в URL-адресу та не діліться ним; тримайте
токен, `.env` та журнали (logs) у таємниці. Уже встановлений робочий простір не
потребує ще одного токена налаштування.

<a id="choose-access"></a>

## Вибір доступу

- **HTTPS домен (рекомендовано):** програма встановлення запускає вбудований проксі Caddy.
  Введіть піддомен, який ви контролюєте, наприклад `campaigns.example.com` (замініть
  на власний), **без схеми, порту чи шляху**. Спрямуйте DNS-запис
  `A` цього імені хоста на цей сервер, дозвольте TCP 80/443 і перевірте
  довірений сертифікат ззовні. Використовуйте `AAAA` лише за наявності робочого IPv6.
- **Локальний / SSH-тунель:** прив'язує програму до loopback-інтерфейсу VPS. Відкрийте її через
  довірений SSH-тунель зі свого комп'ютера; `localhost` вашого ноутбука — це не
  VPS.
- **Публічна IP-адреса + HTTP:** явна згода на незашифрований доступ через порт 8080.
  Паролі, токени та сесії можуть бути перехоплені; **не для безпечного
  використання в робочому середовищі (продакшені)**.

Див. [збірник команд для налаштування](docs/install.md#guided-setup-command-cookbook)
для отримання точних команд, опцій, локального SSH-тунелювання, діагностики та попереджень.

<a id="moving-from-http-to-https"></a>

## Перехід з HTTP на HTTPS

Спершу зробіть резервну копію. Спрямуйте **ваше фактичне ім'я хоста** на VPS, звільніть/відкрийте TCP 80/443
і підтвердьте, що його DNS працює. На VPS, в **наявному** каталозі проєкту:

```sh
./setup.sh --mode https --host campaigns.sendrepute.com
```

Замініть `campaigns.sendrepute.com` на ваше ім'я хоста (`campaign` та
`campaigns` — це різні DNS-імена). Підтвердьте зміну рівня відкритості (exposure) під час запиту;
програма встановлення запускає Caddy, але не перезаписує збережену публічну URL-адресу (Public URL) встановленого робочого простору. Після перевірки HTTPS ззовні, змініть цю URL-адресу у **Workspace
Settings** на `https://YOUR_HOSTNAME/campaigns/`. Якщо використовується Cloudflare, використовуйте
**Full (strict)**, і в жодному разі не Flexible. Див.
[кроки міграції](docs/install.md#migrate-an-installed-public-ip-http-workspace-to-https)
перед зміною активної (live) інсталяції.

## Завантаження v0.1.41

Адміністратори можуть перевіряти наявність стабільних релізів GitHub у Workspace Settings. Перевага надається офіційному версіонованому архіву релізу та вкладенням із контрольними сумами SHA-256. Якщо ці очікувані вкладення відсутні, засіб перевірки може натомість розв'язати той самий стабільний тег релізу в офіційному репозиторії до його незмінного коміту та перевірити маніфест контрольних сум `downloads/`, прив'язаний до цього коміту. Посилання на завантаження з репозиторію закріплені за цим комітом, а не за рухомим тегом чи гілкою. Недійсні або дубльовані очікувані вкладення в жодному разі не дозволяють такий резервний перехід (fallback). У налаштуваннях відображається сповіщення про оновлення, посилання на завантаження/контрольні суми та задокументована команда ручного оновлення сервера для наявного клону Git; програма ніколи не встановлює, не розпаковує та не виконує завантажене. Спершу зробіть резервну копію інсталяції, а потім виконайте процедуру оновлення та перезапуску для оператора. Архівні інсталяції мають дотримуватися окремих інструкцій з оновлення для архівів і перевіряти завантажені байти за контрольними сумами. Збої GitHub, відсутні або неправильно сформовані метадані публікації та невідомі встановлені версії відображаються як недоступні, і ніколи як актуальні. Нові архіви релізів містять метадані своєї встановленої версії; старіші інсталяції без цих метаданих не можуть заявляти про свою актуальність. Публікація релізу та контрольні суми є окремими кроками оператора, які не виконуються самою програмою.

Віддаєте перевагу версіонованому архіву? Завантажте [ZIP](https://github.com/sendrepute/sendrepute-campaigns/raw/refs/tags/v0.1.41/downloads/sendrepute-campaigns-0.1.41.zip)
або [tar.gz](https://github.com/sendrepute/sendrepute-campaigns/raw/refs/tags/v0.1.41/downloads/sendrepute-campaigns-0.1.41.tar.gz),
перевірте [контрольні суми SHA-256](https://github.com/sendrepute/sendrepute-campaigns/blob/v0.1.41/downloads/sendrepute-campaigns-0.1.41-SHA256SUMS),
розпакуйте та запустіть `./setup.sh` там. Це завантаження з репозиторію, а **не**
бінарні вкладення GitHub Release; **Code → Download ZIP** — це інший
знімок стану (snapshot). Див. [примітки до випуску v0.1.41](https://github.com/sendrepute/sendrepute-campaigns/releases/tag/v0.1.41).

<a id="additional-tracking-hostnames"></a>

## Додаткові імена хостів для відстеження

Коли вбудована інсталяція HTTPS/Caddy вже працює, відкрийте **Domains**,
створіть перевірку (challenge) для імені хоста, додайте його запис A/AAAA, спрямований на цей сервер, і
точно відображений TXT-запис підтвердження власності, після чого натисніть **Check DNS and verify**.
Campaigns автоматично додає підтверджене ім'я хоста до того ж керованого проксі
і повторно використовує первинний сертифікат, коли його SAN охоплює це ім'я хоста, інакше
запитуючи автоматичний сертифікат. Повторіть для кількох імен хостів; жодних консольних
команд для окремих доменів чи редагування проксі не потрібно, а первинне ім'я хоста
інсталяції та налаштування сертифіката залишаються незмінними. Обирайте бажане перевірене
ім'я хоста незалежно в кожній кампанії у випадному списку **Tracking domain**.

Схвалення DNS, завантажена конфігурація проксі та працюючий публічний HTTPS відображаються
окремо. Завантаження конфігурації не підтверджує випуск ACME або публічну
доступність. Охоплені імена Origin CA вимагають проксіювання Cloudflare і не є
безпосередньо довіреними для браузерів. DNS та порти 80/443 повинні досягати наявного проксі; Cloudflare
має дозволяти ACME та залишатися **Full (strict)**. Зовнішні проксі/тунелі вимагають
налаштування оператором. Якщо керований проксі не працює або первинне
ім'я хоста відсутнє, доповнення залишаються в черзі до усунення цієї проблеми
рівня інсталяції. Жодного резервного переходу на небезпечний SSL не виконується.

Раніше схвалені маршрути зберігаються у разі видалення домену, доступного для вибору,
або під час ротації його перевірки (challenge), тому доставлені посилання не анулюються приховано.
Зберігайте їхні DNS та оновлення сертифікатів доступними. Зберігайте реєстр
схвалень PostgreSQL та томи HTTPS/Caddy під час оновлень/резервних копій. Інсталяції з ручним первинним
сертифікатом можуть ненадовго переривати з'єднання під час
контрольованого оновлення/перезапуску виключно Caddy. Див. запакований `SMTP-TRACKING.md`
для визначень статусів, збереження історичних посилань та меж відмов/повторних спроб.

<a id="update"></a>

## Оновлення

Спершу зробіть резервну копію; див. [Оновлення](#back-up).
На VPS, **всередині вашого наявного клону Git** (не свіжого клону), перевірте
локальні зміни, після чого виконайте:

```sh
git status --short
git pull --ff-only && ./setup.sh --mode resume
```

`resume` зберігає наявний режим доступу, зокрема HTTPS. Якщо pull відмовляє,
узгодьте зміни замість примусового скидання. Збережіть `.env`, той самий проєкт
Compose, томи PostgreSQL і програми, а також ключ шифрування. Ніколи не запускайте
`docker compose down -v` на реальних даних. Для оновлення з архіву використовуйте
[інструкції з оновлення](docs/operations.md#upgrade), а не новий клон поверх
інсталяції.

<a id="back-up"></a>

## Резервне копіювання

Збережіть повну базу даних PostgreSQL, дані програми/ключ шифрування,
приватний `.env` та стан HTTPS/Caddy. Виконайте
[команди повного резервного копіювання Docker](docs/operations.md#docker-infrastructure-backup),
потім зберігайте зашифровані, захищені копії поза хостом. Експорт JSON у програмі
не є резервною копією інфраструктури та пропускає збережений реєстр схвалень HTTPS,
включно зі схваленими іменами хостів, рядки доменів для вибору яких були видалені.

Для **запланованих за бажанням** зашифрованих резервних копій поза хостом використовуйте включені
`backup.sh`, `backup.conf.example` та приклади systemd. Програма встановлення нічого не планує
і не вмикає. Встановіть `age` та налаштуйте наявний змонтований каталог поза хостом
або обмежене місце призначення SFTP. Залиште обидва налаштування age порожніми:
перша інтерактивна резервна копія автоматично створює свій файл відновлення і просить
вас зберегти окрему безпечну копію перед продовженням. Наступні резервні копії використовують його повторно;
немає команд генерації ключів або значень відкритого ключа для копіювання в конфігурацію.
Хост зберігає захищену копію для перевірки кожної резервної копії; ніколи не зберігайте вашу
незалежну копію відновлення поруч із зашифрованими архівами резервних копій.
Див. [автоматизовані резервні копії](docs/operations.md#opt-in-encrypted-scheduled-backups)
щодо передумов, безпечної активації, перевірки та відновлення. Зі встановленого
каталогу `./backup.sh status` показує останню спробу, останній успіх та архів;
це залишається читабельним, якщо ідентифікатор age або інструменти резервного копіювання недоступні, за умови,
що приватна конфігурація оператора та локальний файл spool/статусу є непошкодженими.
`./backup.sh verify /private/path/archive.tar.age` перевіряє розшифрування, маніфест і
формат PostgreSQL без відновлення даних.

<a id="restore"></a>

## Відновлення

Відновлюйте лише з перевіреної, відповідної резервної копії PostgreSQL **та** тому даних;
експорт JSON у програмі пропускає завдання розсилки, події аудиту та інший стан
середовища виконання. Відновлення може перезаписати новіші дані або відновити розсилку листів із черги. Виконайте
[кроки ізольованого відновлення](docs/operations.md#restore-to-an-empty-isolated-installation)
перед будь-яким перемиканням (cutover) у робоче середовище.

<a id="release-boundary"></a>

## Межі релізу

Реліз містить скомпільовані браузерну і серверну частини, міст доставки та клієнтського API,
публічний клієнтський SDK, міграції та документацію. Він не включає головний
сайт і сканер SendRepute, вміст бази даних, секрети, карти коду, тести
та інструментарій розробки. Умови ліцензій на компоненти та від третіх сторін залишаються
чинними; автономний хостинг не надає ліцензії на хмарний сервіс або гарантії
потрапляння в папку «Вхідні».
